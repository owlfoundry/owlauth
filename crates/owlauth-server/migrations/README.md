# OwlAuth database migrations

Versioned PostgreSQL migrations for OwlAuth's authoritative state belong in this directory.

The target schema stores Project-scoped Applications, provider registrations and secret references, users and linked identities, login transactions, handoff tickets, browser and Application sessions, refresh families, public key metadata, deployment-operator idempotency records, and audit events. Project ownership must be enforceable through direct or composite database constraints; Redis is never authoritative for these records.

SQLx 0.9 embeds these migrations into the `owlauth-server` artifact and applies compatible pending migrations before either Runtime or Control reports readiness. Migration execution uses a dedicated connection, a bounded PostgreSQL advisory-lock wait, transactional migration history, and bounded failure reporting. `verify` mode directly checks the exact embedded SQLx history without creating or changing database objects. SeaORM 2 implements ordinary repositories, but SeaORM schema sync and `sea-orm-migration` do not manage the production schema.

Destructive or irreversible migrations require an explicit compatibility, rollout, backup, and recovery design. Expand-and-contract changes must preserve mixed-version operation for the declared rollout window.

The initial migration establishes Project and Application ownership, deployment-operator idempotency, and audit records. The additive Control provisioning/readiness and signing-safety migrations add exact redirect/origin registration, publishable Application identifiers, signing rings and lifecycle operations, Runtime publication leases, provider secret operations, same-Project provider assignments, and revisioned Project policy. The federated-auth foundation migration adds Project users and linked identities, authoritative login/method snapshots, browser and Application sessions, one-use handoffs, Application bindings/materialized projections, strict refresh families/generations, and one-use browser-logout confirmations. The three Block C migrations add passwordless email, managed provider connections, identity lifecycle, and projection authority. Their committed SHA-256 values are frozen by `migrations_checksum_tests`; corrections require a later migration rather than rewriting history. New migrations must use final domain names and preserve the invariants above.

Deployment operators own backup scheduling and restore orchestration. Follow the PostgreSQL documentation and provider guidance for consistent physical backups or managed snapshots, WAL archiving and point-in-time recovery where required, regular restore testing, encryption, access control, and retention. A usable OwlAuth recovery point must keep PostgreSQL, software signer/configuration-secret stores, process configuration, opaque references, and every still-referenced retained key version mutually consistent. Stop serving before rollback, restore that complete set, and start with `OWLAUTH_MIGRATION_MODE=verify`; do not attempt destructive down migrations. Missing external references or required retained keys intentionally close only the affected capability rather than guessing or silently losing identity authority.

The target storage and migration invariants are defined in [`spec/04-storage-and-migrations.md`](../../../spec/04-storage-and-migrations.md).
